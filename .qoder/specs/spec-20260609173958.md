# Multica 协作群 (Room) 功能 -- 综合分析报告 (v2)

## Context

在 multica 项目基础上，新增了"协作群"(Room) 功能，代号 **ChatCollab**，定位是"以群聊为操作系统的多智能体协作平台"。核心理念是将即时通讯与结构化任务跟踪融合，让 @mention 成为任务派发、咨询、审批、仲裁的统一原语。

该功能涉及 **6 张新数据表**、**25+ 个新 API 端点**、**12 个新 Go service 文件**、**18 个前端 API 方法**、**20+ 个前端组件**，以及 WebSocket 实时同步、工作流状态机、后台任务队列等核心子系统。

本报告结合了完整的 Cursor 开发对话记录（3717 行，71 轮用户交互）和代码静态分析，提供全视角的问题识别和优化建议。

---

## 一、设计决策回溯（来自开发对话）

以下关键决策在开发过程中被明确确定，理解它们对后续优化至关重要：

| # | 决策 | 背景 | 影响 |
|---|------|------|------|
| D1 | Room 是独立实体，不绑定 Issue | 避免轻量对话被迫沉重化 | Room 与 Issue 是可选关联 |
| D2 | Manager Agent 不是聊天参与者 | 用户不应感知到 manager 的存在 | manager 输出仅在必要时以系统通知形式显示 |
| D3 | Manager 不能创建/更新 Issue | 防止 manager 在后台创建不可见的 Issue | 三层执行：API 403 + prompt 指令 + runtime config |
| D4 | 不做 DAG 可视化编辑器 | 现阶段用 prompt 驱动工作流 | 工作流完全依赖 LLM 输出 `workflow_action` JSON |
| D5 | 不强制绑定流程角色 | 后续考虑支持 flow 流程图 | 角色绑定从 UI 移除，仅通过 custom prompt 控制 |
| D6 | Agent 回复截断至 500 字符 | 保持聊天可读性，完整内容存 metadata | 前端需要读取 metadata.detailed_explanation |
| D7 | 每 Agent 串行执行 | invocation 层假设每 Agent 同时只运行 1 个 | 与 task 层 max_concurrent_tasks=3 存在语义冲突 |
| D8 | 双轨渲染模型 | 进行中看 invocation 槽位，完成后看 room_message | 两个数据源的时序和位置规则不一致 |

## 二、严重问题 (Critical / P0)

### C1. 跨 Room 消息泄露 -- `ListIssueRoomMessages` 缺少 Room 成员校验

**文件**: `server/internal/handler/room.go:1848-1882`

**问题**: `ListIssueRoomMessages` 通过 `loadIssueForUser` 检查了 issue 权限，但 **未验证 room 成员资格**。`ListRoomMessagesByLinkedIssue` 返回所有设置了 `linked_issue_id` 的消息，包括调用者不在其中的私密 room 的消息。

**影响**: 任何能看到某个 issue 的用户，都能读取与该 issue 关联的所有私密 room 的聊天内容。这是对话中安全审计明确标记的 **P0 安全问题**。

**修复**: 需要在查询前校验调用者是否为对应 room 的成员，或在 SQL 中加入 room 成员 JOIN 过滤。

### C2. TOCTOU 竞态条件 -- 并发调度可导致 Agent 超载

**文件**: `room_router.go`, `mention_dispatch.go`, `room_invocation_worker.go`

**问题**: 至少 4 处存在 "先 `CountRunningInvocationsForAgent` 检查 -> 再入队" 的非原子操作模式。更严重的是：
- invocation 层假设每 Agent 串行（`running >= 1` 就排队）
- 但 manager agent 的 `max_concurrent_tasks = 3`，task 层允许并行 claim
- 没有 `task_id` 的 queued invocation 对 busy check 不可见，导致 queue jumping

**对话记录**: 用户反复报告 "Agent 一直排队" 和 "回答消失"，与此直接相关。

### C3. parseUUID 静默返回零 UUID -- 违反项目约定

**文件**: `server/internal/service/mention_dispatch.go:253-258`

```go
func parseUUID(s string) pgtype.UUID {
    u, err := util.ParseUUID(s)
    if err != nil {
        return pgtype.UUID{}  // 应 panic 而非静默返回
    }
    return u
}
```

CLAUDE.md 明确要求 trusted UUID 使用 `MustParseUUID` (panic on invalid)。零 UUID 被写入 `mention_invocation.target_id` 后，后续解析永远找不到对应 agent 且无日志。

### C4. WebSocket 事件类型声明缺失/不一致

**文件**: `packages/core/types/events.ts`, `packages/core/realtime/use-realtime-sync.ts`

1. `"room:updated"` 和 `"room:members_updated"` 在前端被订阅（line 741, 750），但 **未声明** 在 `WSEventType` union 中
2. `"room:snapshot_updated"` 在 `WSEventType` 中声明了（line 57），但前端**从未订阅**，后端也**从未发布**（仅在 events.go 中定义常量）
3. `WSEventPayloadMap` 中 **所有 room 事件均缺失** payload 类型映射，回退为 `unknown`

### C5. SQL 查询缺少 room_id 作用域

**文件**: `room.sql` (`UpdateRoomMessageMetadata`), `room_workflow.sql` (`UpdateRoomDelivery`, `UpdateRoomTopic`)

这些 UPDATE 仅按 `id` 过滤，无 `AND room_id = $N`。SQL 查询是最后一道防线，handler 层的校验遗漏会导致跨 room 写入。

### C6. API 响应未使用 Zod Schema -- 违反 API 兼容性规则

**文件**: `packages/core/api/client.ts` (18 个新 room API 方法)

CLAUDE.md 记录了 3 起因相同原因导致的事故 (#2143, #2147, #2192)。所有 room API 方法直接用 `as T` 类型断言返回，无 `parseWithFallback` 验证。对桌面端尤其危险 -- 后端字段变更会导致静默故障或白屏。

### C7. 授权缺口 -- CancelInvocation 无作者/管理员校验

**文件**: `server/internal/handler/room.go:1587-1643`

`CancelInvocation` 仅检查 room 成员资格（`loadRoomMember`），**不验证** 调用者是否为 invocation 的发起者或 room admin。任何 room 成员可以取消其他成员的 @mention 任务。

### C8. 授权缺口 -- DecideApproval 仅需 Room 成员资格

**文件**: `server/internal/handler/room.go:1762-1846`

`DecideApproval` 仅检查 room 成员资格，不检查角色。guest 权限的成员也能批准 agent 的高风险操作。Agent 可以通过 `approval_required` 社工低权限成员来绕过审批。

## 三、高优先级问题 (High / P1)

### H1. `finalizeRoomInvocation` 失败路径导致永久 running

**文件**: `server/internal/service/room_completion.go`

如果 `GetRoom` 失败，函数在 `UpdateMentionInvocationStatus` **之前** 返回。Task 已完成但 invocation 永远停在 `running`。对话中用户多次报告此症状。

**修复**: 重构为先更新 invocation 状态，再创建消息。

### H2. Drain 路径大量静默失败

**文件**: `server/internal/service/room_invocation_worker.go` (DrainQueuedRoomInvocations)

所有错误路径（`GetRoom`, `GetRoomMessageInRoom`, `ResolveRoomMentionAgent`, `EnqueueRoomInvocationTask`）直接 return，不更新 invocation 状态、不写日志。Sweeper 的 `ProcessQueuedRoomInvocations` 仅重新通知已有 `task_id` 的 invocation；**`task_id` 为 NULL 的失败永远不会重试**。

### H3. Agent 空输出被误判为失败

**文件**: `server/internal/service/room_completion.go` (finalizeRoomInvocation)

Daemon 执行时，回答内容通过 `task_message` 流式上报，`output` 字段常为空。当前逻辑在 output 为空时标记 `failed`（"empty agent response"），表现为 "任务成功但协作群显示 Agent 未能完成回答"。

已有 fallback 实现在 `room_task_output.go` 中（从 task_message 提取），但调用链需确保在 output 为空时正确 fallback。

### H4. 双轨渲染模型未对齐

**前端核心问题**。进行中看 invocation 槽位（`RoomInvocationReplySlot`），完成后看 `room_message` 时间线。两个数据源：
- 时序不同：invocation 按触发顺序，message 按 `created_at`
- 位置不同：invocation 锚定在用户消息下方，message 出现在时间线末尾
- 转换时出现短暂闪烁/空白

### H5. Agent 消息位置错位

**文件**: `packages/views/room/room-message-list.tsx`

Agent 完成后，response message 的 `created_at` 是完成时间而非触发时间，导致消息出现在时间线末尾而非触发用户消息下方。DB 有 `response_message_id` 字段但前端未用于锚定。

### H6. Invocation 队列与 Task 队列语义冲突

- invocation 层: `CountRunningInvocationsForAgent >= 1` → 排队（假设串行）
- task 层: manager agent `max_concurrent_tasks = 3`（允许并行）
- 结果: 多个 room invocation 可并行运行，打破 FIFO，导致回复乱序

### H7. `quote_message_id` / `linked_issue_id` 未校验作用域

**文件**: `server/internal/handler/room.go` (SendRoomMessage)

`quote_message_id` 仅验证是否在同一 room 内（`validateRoomQuoteMessage`），但 `linked_issue_id` **未验证** 是否在同一 workspace。可引用其他 workspace 的 issue。

### H8. `RetryInvocation` 忽略 `max_retries`

**文件**: `server/internal/handler/room.go:1512-1585`

Retry handler 不检查 `max_retries` 列，允许无限重试。

### H9. Daemon Room 上下文质量低

**文件**: `server/internal/daemon/execenv/context.go`

Daemon 仅接收最近 30 条 **纯文本** 消息，无 sender/role/@ 结构，无 quote/invocation 元数据。多轮 @ 时 Agent 容易答错轮次。

## 四、中等优先级问题 (Moderate / P2)

### M1. GetRoomWorkboard N+1 查询 + 静默错误

**文件**: `server/internal/handler/room_workflow.go`

关联 issue 逐条 `GetIssueInWorkspace`，多处查询错误被静默忽略（`invocations, _ := ...`）。

### M2. 并发 Delivery 创建竞态

**文件**: `server/internal/service/room_workflow.go` (ensureActiveDelivery)

`ensureActiveDelivery` 先查后建，两个 goroutine 同时调用可创建两个 active delivery。

### M3. resolveRoomTaskBody 阻塞轮询

`time.Sleep(150ms)` 循环最多 5 次，每次任务完成可能阻塞 goroutine 750ms。

### M4. 进度扫描无防抖

多个任务同时完成时，每个都可能触发 manager review，导致重复 dispatch。

### M5. Approval 无超时

`approval_request` 永不超时，关联 invocation 永远停在 pending。

### M6. Fuzzy Agent Name Matching 不可靠

`strings.Contains` 双向匹配，"frontend" 可匹配 "front" 或 "end"。

### M7. 前端 Polling 过于激进

workboard 5s、invocation 3s 无条件轮询，room 不可见时仍轮询。

### M8. 乐观更新逻辑分散

消息发送的乐观更新在 view 组件中而非 mutation hook。

### M9. 模块级内存泄漏

`waitAnchors` Map 无限增长无清理。

### M10. 前端 @mention scope 未限制

room members 加载完成前，@ 可展示所有 workspace 成员/agent/issue。

### M11. Paused Invocation 无 Resume UI

后端有 `ResumeInvocation` API，前端无 "Resume" 按钮。

### M12. 消息无分页

仅拉取 50 条消息，无分页机制。

## 八、架构层面的深度观察

### 8.1 "双轨渲染" 是核心 UX 痛点

从对话记录来看，用户最多的抱怨集中在 "Agent 回答消失"、"回答位置错位"、"一直排队" 这三个问题上。这些问题的根源是同一个：**invocation 和 room_message 是两套数据模型，但前端需要在同一时间线中无缝切换**。

当前架构：
```
用户消息 → MentionInvocation (进行中，显示为槽位)
                ↓ 完成
           RoomMessage (完成后，显示为独立消息行)
```

问题在于：
- invocation 没有 `response_message_id` 到 room_message 的映射（后端有，前端未充分利用）
- room_message 的 `created_at` 是任务完成时间，不是触发时间
- 两者之间的转换没有原子性的 UI 更新机制

**建议**：考虑引入一个 "unified timeline view" 的查询层，在后端合并 invocation 和 message 为一个有序流，避免前端做复杂的双数据源对齐。

### 8.2 Manager Agent 的能力边界问题

Manager 的全部编排能力依赖 LLM 正确输出 `workflow_action` JSON。这是一种 **prompt-as-state-machine** 模式，有以下风险：
- LLM 可能输出格式不正确的 JSON（已有 3 种 fallback 解析策略）
- LLM 可能 "忘记" 输出 workflow_action（对话中多次发生）
- LLM 可能输出错误的 action（如在不该 dispatch 时 dispatch）
- 没有 hard-coded 状态约束来防止非法转换

这在 V1 可以接受，但长远来看需要考虑在 service 层添加状态机约束（如：没有 active delivery 时不允许 `advance_phase`）。

### 8.3 并发模型需要统一

当前存在两层并发控制：
- **Invocation 层**: `CountRunningInvocationsForAgent >= 1` → 排队（严格串行）
- **Task 层**: `max_concurrent_tasks = 3`（允许并行）

这两层的不一致是 "排队永远不消化" 的根因之一。**建议**：room invocation 应该感知 task 层的并发能力，或者反过来，room 任务应该 override `max_concurrent_tasks = 1`。

### 8.4 对话记录中的用户核心诉求总结

从 71 轮用户交互中提炼的核心诉求：

1. **像企微一样干净的聊天体验** -- manager 不可见，系统消息最小化
2. **Agent 必须可靠地完成回答** -- 不能 "一直排队" 或 "回答消失"
3. **回答位置必须正确** -- 在提问下方，不是时间线末尾
4. **不要强制工作流角色绑定** -- 用 custom prompt 控制，未来支持 flow 编辑器
5. **Manager 不能创建 Issue** -- 已实现三层执行

# 协作群 (Room) 全功能交付实施计划

## Context

协作群功能(ChatCollab)已基本搭建完成，但存在多个阻塞性 Bug 和未完成的功能。本计划的目标是让协作群达到**全功能可用**状态 -- 修复所有影响用户体验的问题，补全 PRD 中讨论过但未实现的功能。其他非功能性优化（Zod schema、i18n、测试补充等）全部让路。

本地环境可正常启动运行。

---

## 实施阶段

### Phase 1: 安全与正确性基础修复

这些是功能正常运行的前提条件，必须首先完成。

#### 1.1 跨 Room 消息泄露修复 (C1)

**文件**: `server/internal/handler/room.go` -- `ListIssueRoomMessages`

**当前**: 通过 `loadIssueForUser` 检查 issue 权限，但未验证调用者是否为关联 room 的成员。

**修复**:
- 查询返回的每条消息的 `room_id`，校验调用者是否为该 room 的成员
- 或修改 SQL `ListRoomMessagesByLinkedIssue` 添加 room_member JOIN 过滤
- 返回结果中过滤掉调用者不是成员的 room 的消息

#### 1.2 CancelInvocation 授权校验 (C7)

**文件**: `server/internal/handler/room.go` -- `CancelInvocation`

**当前**: 仅检查 room 成员资格，任何成员可取消他人的 @mention。

**修复**:
- 获取 invocation 的触发者（通过关联的 message 的 sender_id）
- 允许取消的条件：调用者 == 消息发送者 OR 调用者是 room owner/admin

#### 1.3 DecideApproval 权限校验 (C8)

**文件**: `server/internal/handler/room.go` -- `DecideApproval`

**当前**: 仅检查 room 成员资格，guest 也能审批。

**修复**:
- 限制为 role != "guest" 的成员才能审批
- 或更严格：仅 owner/admin 可审批（取决于产品需求）

#### 1.4 WebSocket 事件类型补全 (C4)

**文件**:
- `packages/core/types/events.ts` -- 添加 `"room:updated"` 和 `"room:members_updated"` 到 WSEventType union
- `packages/core/types/events.ts` -- 在 WSEventPayloadMap 中添加所有 room 事件的 payload 类型
- `packages/core/realtime/use-realtime-sync.ts` -- 订阅 `"room:snapshot_updated"` 事件

#### 1.5 SQL 查询添加 room_id 约束 (C5)

**文件**:
- `server/pkg/db/queries/room.sql` -- `UpdateRoomMessageMetadata` 添加 `AND room_id`
- `server/pkg/db/queries/room_workflow.sql` -- `UpdateRoomDelivery`, `UpdateRoomTopic` 添加 `AND room_id`
- 运行 `make sqlc` 重新生成代码

#### 1.6 parseUUID 修复 (C3)

**文件**: `server/internal/service/mention_dispatch.go:253-258`

**修复**: 改为调用 `util.MustParseUUID`（panic on invalid）或根据上下文使用错误返回。

#### 1.7 linked_issue_id 作用域校验 (H7)

**文件**: `server/internal/handler/room.go` -- `SendRoomMessage`

**修复**: 验证 `linked_issue_id` 指向的 issue 在同一 workspace 内。

#### 1.8 RetryInvocation 检查 max_retries (H8)

**文件**: `server/internal/handler/room.go` -- `RetryInvocation`

**修复**: 在 retry 前检查 `inv.RetryCount < inv.MaxRetries`。

### Phase 2: 核心可靠性修复

修复用户最常报告的问题：Agent 卡住、回答消失、消息错位。

#### 2.1 finalizeRoomInvocation 状态更新顺序 (H1)

**文件**: `server/internal/service/room_completion.go`

**问题**: `GetRoom` 失败时函数提前返回，invocation 永远停在 `running`。

**修复**:
- 重构执行顺序：先 `UpdateMentionInvocationStatus` 为 succeeded/failed，再创建 room_message
- 确保所有错误路径都会更新 invocation 状态（即使后续步骤失败）

#### 2.2 Drain 路径错误处理 (H2)

**文件**: `server/internal/service/room_invocation_worker.go`

**问题**: 所有错误路径直接 return，不更新状态、不写日志。

**修复**:
- 每个 return 路径前：更新 invocation 状态为 `failed`（或 `pending` 重试）+ `slog.Warn`
- `ProcessQueuedRoomInvocations`：对无 `task_id` 的失败 invocation 增加重试逻辑

#### 2.3 Agent 空输出处理 (H3)

**文件**: `server/internal/service/room_completion.go`

**问题**: Daemon 通过 `task_message` 流式上报内容，`output` 常为空。当前直接标 failed。

**修复**:
- 确保 output 为空时，先调用 `extractRoomReplyFromTaskMessages` 从 task_message 提取
- 仅在两种方式都无内容时才标 failed
- 验证当前 `resolveRoomTaskBody` 的 fallback 链是否正确连接

#### 2.4 TOCTOU 竞态修复 (C2)

**文件**: `room_router.go`, `mention_dispatch.go`, `room_invocation_worker.go`

**问题**: `CountRunningInvocationsForAgent` + enqueue 非原子操作。

**修复**:
- 在 `CountRunningInvocationsForAgent` 查询中使用 `SELECT ... FOR UPDATE` 锁定相关行
- 或在 `EnqueueRoomInvocationTask` 中使用 PostgreSQL advisory lock：`pg_advisory_xact_lock(agent_id_hash)`
- 确保 room 任务的 `max_concurrent_tasks` 被 override 为 1（与 invocation 层串行假设一致）

#### 2.5 队列语义统一 (H6)

**文件**: `server/internal/handler/room.go` (CreateRoom 中 manager agent), `server/internal/service/mention_dispatch.go`

**修复**:
- 创建 room agent 时 `MaxConcurrentTasks` 保持 3（manager 需要并行 dispatch）
- 但 role agent 的 room invocation 强制串行：在 `dispatchRoomAgentMention` 中，对于非 manager agent，使用 `CountRunningInvocationsForAgent` 基于 `mention_invocation` 表（而非 `agent_task_queue`）的计数
- 或：room invocation 的 drain 逻辑改为只检查 room 级别的 running 数量

### Phase 3: 消息渲染与实时体验

#### 3.1 双轨渲染对齐 (H4/H5)

**文件**: `packages/views/room/room-message-list.tsx`

**问题**: invocation 槽位和 room_message 是两个数据源，转换时闪烁/错位。

**修复**:
- 在 `flattenInvocationChain` 和 `collectAnchoredResponseIds` 中，使用 `response_message_id` 将完成的 invocation 与其 room_message 关联
- 当 invocation 有 `response_message_id` 时，在槽位位置渲染 room_message 内容（而非在时间线末尾）
- 在时间线中过滤掉已被锚定的 room_message（避免重复渲染）

#### 3.2 Agent 回复完整内容显示 (m10)

**文件**: `packages/views/room/room-agent-reply-body.tsx`

**问题**: 回复截断至 500 字符，但 `metadata.detailed_explanation` 包含完整内容，前端未读取。

**修复**:
- 在 `AgentMessageBody` 中，检查 `metadata.detailed_explanation`
- 如有，使用完整内容（或添加 "展开全文" 交互）

#### 3.3 Optimistic 消息 Fake ID 问题 (m11)

**文件**: `packages/views/room/room-view.tsx`

**问题**: 乐观消息用 `optimistic-${Date.now()}` 作为 ID，"创建 Issue" 操作可用此 fake ID 触发 404。

**修复**:
- 在乐观消息上禁用 "创建 Issue" 等操作按钮，直到服务端返回真实 message_id
- 或在 `usePromoteRoomMessageIssue` 中检查 message_id 是否为 optimistic 前缀

#### 3.4 Send debounce 竞态 (m12)

**文件**: `packages/views/room/room-composer.tsx`, `packages/views/room/room-view.tsx`

**问题**: ContentEditor debounce 300ms，但 handleSend 从 React state 读取 draft，快速 Enter 可能发送旧内容。

**修复**:
- `handleSend` 改为从 editor 实例直接获取 markdown（`editor.getMarkdown()`），而非依赖 state

#### 3.5 @mention scope 加载态限制 (M10)

**文件**: `packages/views/room/room-composer.tsx`, `packages/views/editor/extensions/mention-suggestion.tsx`

**问题**: room members 加载完成前，@ 展示所有 workspace 成员。

**修复**:
- 在 roomMembers 加载完成前，不渲染 mention suggestion（或显示 loading 状态）
- 添加 `isRoomMembersLoaded` 条件守卫

### Phase 5: PRD 功能交付

#### 5.1 自动工作流推进

**文件**: `server/internal/service/room_progress.go`, `server/internal/service/room_workflow.go`

**当前**: `MaybeTriggerManagerProgressScan` 和 `enqueueManagerReview` 已实现但不可靠。用户报告工作流经常停滞需要手动催促。

**修复**:
- 确保 role agent 完成后自动触发 manager review（`enqueueManagerReview`）
- 确保 manager review 输出被正确解析为 `workflow_action`
- 确保 `drainRoomDispatchAgents` 在 dispatch 后被正确调用
- 添加进度扫描防抖：使用 advisory lock 或 Redis 锁防止并发扫描
- 验证端到端流程：用户发消息 → manager orchestrate → dispatch role → role execute → manager review → advance phase → 完成

**验证场景**: 用户发送 "开发一个贪吃蛇游戏" → 自动走完 需求分析→设计→开发 三个阶段

#### 5.2 Issue 深度集成 -- 交互式卡片

**文件**: `packages/views/room/room-issue-card.tsx`, `server/internal/handler/room.go`

**当前**: `RoomIssueCard` 是静态链接卡片，Issue 状态变更不会反映在 room 中。

**修复**:
- 利用已有的 WebSocket issue 事件（`issue:updated`）实时更新卡片内容
- 在 `use-realtime-sync.ts` 中，当收到 `issue:updated` 事件时，检查是否有 room 消息 link 了该 issue，如有则 invalidate workboard
- 卡片显示：标题、状态 badge、assignee、优先级
- 状态变更时在卡片上实时更新（而非创建新的系统消息）

#### 5.3 Issue 状态变更回流 Room 聊天

**文件**: `server/internal/service/room_completion.go` (NotifyRoomIssueCreated 扩展)

**修复**:
- 当关联的 issue 状态变更时，在 room 中发送系统消息（或在现有卡片上更新）
- 利用 `issue.source_room_id` 和 `issue.source_message_id` 找到关联的 room
- 通过 WebSocket 推送更新

#### 5.4 @member / @issue / @all 实现或移除

**文件**: `packages/views/editor/extensions/mention-suggestion.tsx`

**当前**: composer 展示这些选项但后端静默忽略。

**修复**:
- 短期：从 mention suggestion 中移除 `@member`（全员）、`@issue`、`@all` 选项，避免用户困惑
- 或实现基本功能：`@all` 通知所有 room 成员（创建 system message）

#### 5.5 Room 管理功能完善

**文件**: `packages/views/room/room-settings-sheet.tsx`

**修复**:
- 添加 room 删除功能（永久删除，区别于 archive）
- 或确认 archive 即为最终操作
- 确保 archive 后正确导航（已有 `removeQueries`）
